## dsh 新发现（P0，仅干净机器暴露）

```
[aimail-hub] start failed: ENOENT: no such file or directory, rename
  '/home/runner/.dsh/profiles/web/aimail/status.json.tmp'
  -> '/home/runner/.dsh/profiles/web/aimail/status.json'
=> the agent never bound: no complete agentmail.json within 300s
```
写入点 `tssdk/packages/agent-aimail/src/dsh/mail-hub.ts:513-517` 本身有
`await fs.mkdir(path.dirname(p), { recursive: true })`，但 CI 干净 HOME 上 rename 仍 ENOENT。
两种可能，需开发用干净 HOME 复现定位：
1. mkdir 的 `p` 与 rename 的 `p` 不是同一路径（`statusPath()` 依赖 `dshHome()`/`profile()`，
   若两者在 mkdir 与 write/rename 之间取值变化，tmp 与目标就分属不同目录）；
2. mkdir 与 rename 之间该目录被删除（并发 hub 实例/清理逻辑）。

补充：`writeStatus()` 本身（mail-hub.ts:508-517）逻辑是自洽的——同一个 `p`、先 mkdir 再
writeFile(tmp) 再 rename。所以问题更可能在 `statusPath()` 的输入在运行期变化，或存在并发实例。
`ENOENT` 在 rename 上也可能指**源文件不存在**（即 writeFile 写到了另一处），建议开发先用
`strace -f -e trace=mkdir,open,rename` 在干净 HOME 下抓一次。

**为什么 L2 没抓到（更正后的解释）**：两层测试的差异在"谁装 SDK"，不在 home 是否干净——
两层都是**干净的宿主环境 + 预装 LLM 配置**。

| 层 | SDK 来源 | 安装时机 | 对 `~/.dsh` 的影响 |
|---|---|---|---|
| L2 | **开发版**（fixture 主动装） | 宿主启动前，由夹具在容器内执行安装 | 安装期的副作用（含目录创建）**先于** bind 发生 |
| L3 | **已发布版**（不主动装） | 激活过程中由 agent 按提示引导安装 | 首次写 `status.json` 之前，只有引导安装这条路径跑过 |

所以 ENOENT 最可能的分歧点是**两条安装路径的副作用不同**：夹具的主动安装会创建
`~/.dsh/profiles/web/aimail/`（或触发 postinstall 建目录），而引导安装这条路径在 hub 启动前
没有把该目录建出来。请开发对比两条安装路径对 `~/.dsh` 的落盘差异，而不是去查"home 脏不脏"。
