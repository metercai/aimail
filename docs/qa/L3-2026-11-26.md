## dsh 新发现（P0，仅干净机器暴露）

```
[aimail-hub] start failed: ENOENT: no such file or directory, rename
  '/home/runner/.dsh/profiles/web/aimail/status.json.tmp'
  -> '/home/runner/.dsh/profiles/web/aimail/status.json'
=> the agent never bound: no complete agentmail.json within 300s
```
写入点 `tssdk/packages/agent-aimail/src/dsh/mail-hub.ts:513-517` 本身有
`await fs.mkdir(path.dirname(p), { recursive: true })`，但 CI 干净 HOME 上 rename 仍 ENOENT。
两种可能，需开发用干净 HOME 复现定位：
1. mkdir 的 `p` 与 rename 的 `p` 不是同一路径（`statusPath()` 依赖 `dshHome()`/`profile()`，
   若两者在 mkdir 与 write/rename 之间取值变化，tmp 与目标就分属不同目录）；
2. mkdir 与 rename 之间该目录被删除（并发 hub 实例/清理逻辑）。

补充：`writeStatus()` 本身（mail-hub.ts:508-517）逻辑是自洽的——同一个 `p`、先 mkdir 再
writeFile(tmp) 再 rename。所以问题更可能在 `statusPath()` 的输入在运行期变化，或存在并发实例。
`ENOENT` 在 rename 上也可能指**源文件不存在**（即 writeFile 写到了另一处），建议开发先用
`strace -f -e trace=mkdir,open,rename` 在干净 HOME 下抓一次。

**为什么 L2 没抓到（更正后的解释）**：两层测试的差异在"谁装 SDK"，不在 home 是否干净——
两层都是**干净的宿主环境 + 预装 LLM 配置**。

| 层 | SDK 来源 | 安装时机 | 对 `~/.dsh` 的影响 |
|---|---|---|---|
| L2 | **开发版**（fixture 主动装） | 宿主启动前，由夹具在容器内执行安装 | 安装期的副作用（含目录创建）**先于** bind 发生 |
| L3 | **已发布版**（不主动装） | 激活过程中由 agent 按提示引导安装 | 首次写 `status.json` 之前，只有引导安装这条路径跑过 |

所以 ENOENT 最可能的分歧点是**两条安装路径的副作用不同**：夹具的主动安装会创建
`~/.dsh/profiles/web/aimail/`（或触发 postinstall 建目录），而引导安装这条路径在 hub 启动前
没有把该目录建出来。请开发对比两条安装路径对 `~/.dsh` 的落盘差异，而不是去查"home 脏不脏"。

## 本地复跑（2026-11-26，干净 HOME + 预装 LLM 配置 + 已发布 SDK 0.6.0）

```
✓ agent bootstrapped the plugin itself: agent-aimail@0.6.0 (= npm latest)
✓ bind → owner-only(600) → no webhook_url → SSE streams up
✓ 身份卡 + 邮件签名生效；query-mail 签名断言通过
✓ L3 PASS: linux-amd64 / dsh   (llmMs 89881, rc=0)
```
**本地不复现 CI 的 ENOENT** ⇒ 更可能是**并发写竞态**，而不是"目录不存在"：

```ts
const tmp = `${p}.tmp`     // 所有写入者共用同一个 tmp 名
await fs.writeFile(tmp, ...)
await fs.rename(tmp, p)    // 两个 hub 同时写：先到者移走 tmp，后者 rename ⇒ ENOENT
```
L3 第 4 步是"host restart（插件安装生效需重启）"——旧 hub 未完全退出、新 hub 已启动时就有两个写入者。
CI 机器慢、重叠窗口大 ⇒ 失败；本地快 ⇒ 躲过。

**修法**：tmp 名带 pid/随机后缀，或把 `writeStatus()` 串行化。
**验收**：CI 四个平台的 dsh 连跑两次均 PASS。

## 跨宿主共性缺陷（本地 L3 追加，2026-11-26）

三个宿主各自以不同形态卡住，但瓶颈同一个：**激活邮件只给方向，不给可执行命令**。

邮件原文：
> If your agent does not have `aimail_address`, install or enable the AIMail plugin
> through your host's **normal plugin/extension mechanism** (not the aimail install CLI).

| 宿主 | 观察到的行为 | 证据 |
|---|---|---|
| hermes | 不装，改为**阅读仓库里的证据文档**并汇报（把任务当调查） | 该轮输出引用了 `evidence/l3-hermes-...md` |
| openclaw | 想执行但工具面失败：`[tools] dispatch_action failed`，随后自查网关状态 | `oc-turns.log` |
| pi（CI macos） | `agent never installed agent-aimail` | CI 日志 |

**判定**：这是 L3 才暴露的产品/UX 缺陷——L2 由夹具主动装 SDK 绕过了它，而真实用户只拿到这封邮件。
**修法建议（给开发）**：邮件正文给出**逐宿主的可复制命令**（`pip install agent-aimail==0.4.0` / `openclaw plugins install agent-aimail` / `pi install agent-aimail@latest`），或提供一条 `aimail bootstrap <host>` 让 agent 直接执行；并在正文里明确"现在执行下面这行"。
**验收**：任一宿主在**不给 nudge** 的情况下，单轮内自行完成安装、绑定并回信。

## 本地快循环得到的三条确定事实（2026-11-26 追加）

用「prepare 一次 → 只重跑失败步」把 12 分钟一轮压到 1–5 分钟后，拿到：

1. **hermes 的工具面正常**：`hermes --yolo -z "touch /tmp/hx2/TOOL_OK …"` → 文件真的被创建；
2. **安装命令本身正常**：`pip install agent-aimail==0.4.0` 20 秒装好；
3. **真正卡住的是夹具的 nudge 写法**：原 nudge 写着 "then retry the activation"，agent 会去绑定（那时绑定条件未就绪）并反复重试直到超时。
   改成「只装、别绑定」后，hermes 200 秒内回报 `agent-aimail 0.4.0 installed`。
   ⇒ 已改：安装与绑定是两个独立回合（`journey-hermes.sh` / `journey-openclaw.sh`）。
