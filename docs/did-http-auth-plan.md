# SDK ↔ Gateway 信任模型重构：DID 签名的 HTTP 请求（评估方案）

> 状态：**评估中，未执行**。这是与主方案（`docs/did-vc-email-authenticity-plan.md`）**并列的第二份方案**，
> 只在 Q2 议题下评审，不并入 P0–P8。
> 目标：回答三个问题——**难不难**、**安全增益够不够**、**算力代价多大**。

---

## 0. 一页结论

**提议**：把「API key + HMAC」换成「DID 私钥签名的 HTTP 请求」。
注册阶段用现成的 `GatewayAccess-v1` 挑战一次，之后每个请求用 Ed25519 签。

**三个数字先给**（本机实测，OpenSSL 后端，含 Python 调用开销）：

| 操作 | 耗时 | 吞吐（单核） |
|---|---|---|
| Ed25519 验签（64 B 消息） | **128 µs** | 7 800 op/s |
| Ed25519 签名 | 35 µs | 28 700 op/s |
| HMAC-SHA256（现方案，~90 B 基串） | **1.8 µs** | 543 000 op/s |
| SHA-256（4 KiB body） | 3.5 µs | — |

→ 每请求多花约 **126 µs**。10 rps 占单核 0.13%，100 rps 占 1.3%，1000 rps 占 13%。
**算力不是障碍**；真正的代价在"`did:key` 不能轮换"和"迁移期双栈"。

**安全增益**：一句话——**服务商库里再没有任何能冒充用户的秘密**。
现在的 `api_keys.key_hash` 就是 HMAC 密钥，数据库/备份泄露即等于所有地址被完全接管；
新模型下库里只有"哪个 DID 绑了哪个地址"，没有签名能力。这同时让 HTTP 层服从主方案 §9 的公理一
（服务商不得代表用户）。

**最难的两条负面都能解**：① `did:key` 不可轮换 → 一个地址绑 **多个 DID**，轮换＝加新→切 primary→删旧；
② seed 泄露影响面变大 → **按用途分离**两把 DID（`mail-signing` 由安全员审批、`api-access` 自持）。
代价只是 `did_bindings` 从 1:1 变成 1:N 并多一个 `purpose` 字段（§2.5、§3.3）。

**代价的真实规模**：收信走 SSE 长连接，鉴权摊在建连与零星请求上，**不是每封信**（§4.4）。
真正按请求计的是发信与 API 调用，量级远低于"每封邮件一次验签"的直觉。

**难易度**：中偏高。代码量不算大，但它动的是**全局鉴权路径**——错一次就是所有请求 401 或全部放行。
集中风险在 gateway 的 `auth.rs`（1 182 行）+ 三端签名器 + 一张新表 + 一个注册端点。

**建议**：单独立项（H 系列），排在 P8 之后；但其中一项**现在就该做**——
把 `did_bindings`（DID → 地址 → 作用域）落进 P7 的绑定审批流程，
这样 H 开始时数据已经在了（见 §9.3）。

## 1. 现状：今天的信任模型

| 环节 | 事实 | 依据 |
|---|---|---|
| 密钥形态 | 网关生成的随机 API key | 激活流程发放 |
| 服务端存什么 | `api_keys.key_hash = sha256(raw_key)` | 该值**就是** HMAC 密钥 |
| 请求怎么签 | `HMAC-SHA256(key_hash, METHOD\nPATH\nTIMESTAMP\nBODY_SHA256)` | `docs/API-SIGNATURE-PROTOCOL.md` |
| 身份怎么带 | `X-Api-Identity`（地址或 system_id）+ `X-Api-Signature` + `X-Api-Timestamp` | 三端各有实现与同一份向量 |
| 拉信怎么认 | `X-Aimail-Anchor`（`sha256(email + NUL + anchor)`） | 与密钥并存 |

**三条结构性弱点**：

1. **库泄 = 全面冒充**。`key_hash` 是 HMAC 密钥，拿到它就能为任意地址构造任意请求，
   包括发信、拉信、改配置。这是"持有一份可用凭据"，不是"持有一份可验证的公钥"。
2. **服务商能代表用户**。网关自己持有 `key_hash`，理论上可以替用户构造请求——
   与邮件签名那条"服务商不得代签"的公理（主方案 §9）在同一侧却给出了相反结论。
3. **四套互不相关的标识**：`api_key`、`X-Api-Identity`、`anchor_id`、`did`（引入 DID 后）。
   四处都要保持一致，任一处漂移就是配置错误。

## 2. 目标模型：两段式

### 2.1 注册阶段：挑战一次（复用 `GatewayAccess-v1`）

```text
agent                                        gateway
  │  1. 生成 did:key（本地，不导出私钥）          │
  │  2. POST /api/v1/did/enroll  {did, address}  │
  │  ─────────────────────────────────────────►  │
  │                                              │  校验：激活码/审批单 + 地址归属
  │  3. 200 {challenge, expires_at}              │
  │  ◄─────────────────────────────────────────  │
  │  4. sign("GatewayAccess-v1\n{did}\n{addr}\n{challenge}")
  │  5. POST /api/v1/did/enroll  {…, s}          │
  │  ─────────────────────────────────────────►  │  离线解 did:key 得公钥 → 验签
  │                                              │  写 did_bindings(did, address, scopes, active)
  │  6. 200 {binding_id}                         │
  │  ◄─────────────────────────────────────────  │
```

`GatewayAccess-v1` 是 did-sdk 里**早已存在、从未被生产代码使用**的签名对象
（`keyvault-core/src/signing_input.rs:54`），契约注明用途 "HTTP gateway auth"——正是这里。
两端绑定都已导出，且有现成向量，不需要新造格式。

### 2.2 稳态：每请求签一次

签名基串（七行，每行尾随 `\n`，与主方案其它对象同一约定）：

```text
AIMail-Request-v1
{METHOD}            # 大写
{PATH_AND_QUERY}    # 线路上发送的原始 target，含查询串，保持 URL 编码
{T}                 # Unix 毫秒
{BODY_SHA256}       # body 的小写 hex；空 body 用 sha256("")
{DID}
{ADDRESS}           # 本请求代表的地址，小写
```

头（沿用主方案的 `k=v; 引号` 风格，复用同一套参数解析器）：

```text
Authorization: AIMail-DID v=1; did="did:key:z6Mk…"; addr="alice@example.com"; t=1765144656789; s=<base64url>
```

`did` 与 `addr` **必须进签名基串**，否则把签名搬到另一个地址上就成立了。

### 2.3 时间窗与重放

- 时间窗：`now-300s ≤ t ≤ now+5s`（与主方案 `DID-Signature` 同一套窗口语义，同一套时钟偏差处理）。
- 重放：**当前 v1 协议也没有 nonce**，所以这不是回归。可选加固：写操作带 `X-Aimail-Nonce`，
  服务端对 `(did, nonce)` 做有界 LRU 去重；读操作天然幂等，不需要。

### 2.4 授权来源：本地绑定记录，不是链上有效期

这是**必须分清**的一处：

| 问题 | 谁回答 | 数据源 |
|---|---|---|
| 这个 DID 能否以这个地址发请求 | `did_bindings` 表（`active` 标志） | 本地库 |
| 这个 DID 是否仍能签邮件 | `EmailBinding` 锚定的 `revoked` / `valid_until` | 链 |

**锚定到期不应该让 agent 连 API 都进不去**——收信是拉取模型，吊销 API 等于让人失联。
所以 `valid_until` 只影响 `DID-Signature` 的裁决，不影响 HTTP 鉴权；只有显式撤销绑定
（运营动作）才关掉 API 访问。

### 2.5 多 DID 绑定与按用途分离（解决"不可轮换"与"爆炸半径"）

`did:key` 不能轮换，这是新模型最大的负面。两条设计把它压回去：

**① 一个地址绑多个 DID（`did_bindings` 是 1:N，不是 1:1）**

```text
did_bindings(did PK, address, purpose, primary, active, approved_by, approved_at)
                  索引: (address, purpose, primary)
```

- 轮换流程＝**加新 DID → 切 primary → 移除旧 DID**，全程不换地址、不重走审批的"地址归属"部分；
- 邮件签名始终只认 `primary=1 AND purpose='mail-signing'` 的那一把，
  "一个时刻只有一个签名 DID"这条不变量不变；
- 旧 DID 保留一段时间（灰度/对账），到期删除。

**② 按用途分离 DID（降低爆炸半径）**

| 用途 | 谁审批 | 存放 | 泄露影响 |
|---|---|---|---|
| `mail-signing` | **安全员**（签发 `EmailBindingVC`） | 设备安全区/受保护文件 | 可伪造该地址的签名邮件 |
| `api-access` | agent 自持（注册时挑战自证） | 同一 keystore，不同密钥 | 可读写该地址的 API |

两条分开之后：

- seed 泄露不再"签名 + API 一起丢"——哪把泄露处理哪把；
- 但也不会退化成"需要一个共享秘密"——两把都是公钥可验的 DID；
- 代价：agent 要管两把钥匙；`did_bindings` 多一个 `purpose` 维度。

如果选择**一把 DID 走天下**（更简单），就要接受"泄露即全丢"，并把"重新绑定"当成常规运维动作写进手册。

## 3. 安全评估

### 3.1 威胁对照

| 威胁 | 今天（API key + HMAC） | 新模型 | 判定 |
|---|---|---|---|
| **数据库/备份泄露** | **全面冒充**：`key_hash` 即 HMAC 密钥 | 只泄露 did→地址映射；无签名能力 | **显著改善**（核心收益） |
| **服务商内部人冒充用户** | 可行（持有 `key_hash`） | 不可行（没有私钥） | **显著改善**，且与公理一一致 |
| 网关进程内存被读 | 可拿到 HMAC 密钥 | 只能拿到公钥 | 改善 |
| **agent 主机被入侵** | 拿到 api_key → 可发信/拉信 | 拿到 seed → 可发信/拉信/签邮件 | 略差（原来只丢 API，现在连签名一起丢） |
| **私钥丢失** | 换一把 API key 即可 | **换 DID = 重新审批绑定**（`did:key` 不可轮换） | **明显变差**（最大代价） |
| 重放 | 300 s 窗口，无 nonce | 同样 300 s 窗口，无 nonce | 持平（可选 nonce 加固） |
| 跨地址冒用 | 靠 `X-Api-Identity` 与 key 绑定 | 地址进签名基串，改了就验签失败 | 改善 |
| TLS 被终止/中间人 | HMAC 仍能保护 body | Ed25519 同样保护 | 持平 |
| 传输成本 | 3 个头 | 1 个头 | 改善（略） |

### 3.2 两个必须写进对外文档的边界

1. **不能替代 TLS**。签名证明"谁发的"和"内容未改"，不提供机密性；窃听者仍能读明文。
2. **`did:key` 没有轮换**。seed 一旦泄露，唯一处置是换 DID 并走一遍重新绑定审批。
   这与"API key 泄露可以立刻换一把"是量级不同的运维成本，必须让人预先知道。

### 3.3 负面清单与缓解（逐条）

| # | 负面 | 严重度 | 缓解 | 残余风险 |
|---|---|---|---|---|
| 1 | `did:key` **不可轮换** | 高 | 多 DID 绑定（§2.5①）：加新 → 切 primary → 删旧 | 轮换需要一次签发动作，不能"就地换钥匙" |
| 2 | seed 泄露影响面变大 | 高 | 按用途分离两把 DID（§2.5②） | 同一台主机上两把钥匙都可能在磁盘 |
| 3 | 每请求多一次 Ed25519 | 低 | 实测 128 µs/请求（Python）；Rust 预期 50–70 µs；必要时切会话令牌（§7） | 高 QPS 建的连需要复核 |
| 4 | 迁移期双栈 | 中 | H2–H4 分三期，配置开关 `aimail_auth=hmac|did` | 双栈期间两条鉴权路径都要测 |
| 5 | 客户端复杂化 | 低 | 签名逻辑收进 did-sdk helper，SDK 只调一行；仍可作为可选 extra | 未装 extra 的 agent 只能用 v1 |
| 6 | 撤销耦合（绑定没了→API 也没了） | 中 | **已解耦**：API 看 `did_bindings.active`，邮件看锚定生命周期（§2.4） | 安全事件下仍需一键停 API |
| 7 | 重放 | 低 | 与现状持平（都只有时间窗）；可选 `X-Aimail-Nonce` | 300 s 窗口内的重放仍可能 |
| 8 | 鉴权是全局路径，改错即全站 401/全放行 | 中偏大 | 认证矩阵测试 + 灰度 + 双栈回退 | — |
| 9 | 需要一次性解决"注册前没有身份" | 中 | 复用 `GatewayAccess-v1` 挑战完成注册（§2.1） | 注册端点本身要有防滥用限速 |

**结论**：1、2 两条最痛，但都有干净解法（多 DID + 按用途分离），代价是 `did_bindings` 从 1:1 变成 1:N
并多一个 `purpose` 字段。其余是可管理的工程成本。

## 4. 算力评估

### 4.1 实测（本机，OpenSSL 后端，含语言调用开销）

| 操作 | µs/op | op/s（单核） |
|---|---|---|
| Ed25519 验签 | 127.7 | 7 830 |
| Ed25519 签名 | 34.8 | 28 700 |
| HMAC-SHA256 | 1.84 | 542 775 |
| SHA-256 / 4 KiB | 3.5 | 285 779 |
| SHA-256 / 64 KiB | 50.2 | 19 904 |

注 1：这是 **Python + OpenSSL** 的测量值，含 Python 调用开销。Rust `ed25519-dalek` 单笔验签预期
**50–70 µs**；**H1 必须用 criterion 在目标硬件上实测确认**，本方案不拿 Python 数字当结论。
注 2：批量验签（dalek batch）对 HTTP 请求-响应模型没有收益，不列入方案。

### 4.2 每请求增量的构成

| 环节 | 今天 | 新模型 | 增量 |
|---|---|---|---|
| 请求体摘要 | SHA-256(body) | 同 | 0 |
| 认证 | HMAC-SHA256 ≈ 1.8 µs | Ed25519 verify ≈ 128 µs | **+126 µs** |
| 额外的 DB 查询 | 1 次（按 key_hash） | 1 次（按 did） | 0 |

### 4.3 容量推算

| 请求速率 | 认证占用（单核） |
|---|---|
| 10 rps | 0.13% |
| 100 rps | 1.3% |
| 1 000 rps | 13% |

### 4.4 负载从哪里来（关键：不是每封信）

aimail 的收信是 **SSE 长连接拉取**（`pysdk/v2/pull_client.py` 的 `stream_path`），
所以鉴权发生在**建连**与 pending/ack 这类零星请求上，**不是每封邮件**。粗略分类：

| 请求类型 | 频率 | 是否每次都要验签 |
|---|---|---|
| 发信 `/api/v1/send` | 每封信一次 | 是 |
| SSE 建连 / 重连 | 每连接（长连） | 是（建连时） |
| pending / ack | 每轮拉取 | 是 |
| 管理类调用 | 低频 | 是 |

所以"每请求 128 µs"实际摊到的总量远小于"每封信"。**H1 阶段需要用真实请求分布复核这条判断**
（尤其是长连断开重连的比率）。

对比网关每封发信已有成本（组 MIME、SQLite 写、投递队列），**126 µs 可以忽略**。
若将来真到 1 000 rps 且成为瓶颈，退路是"挑战换短时会话令牌"（见 §7）；
`ed25519-dalek` 的批量验签对 HTTP 请求-响应模型没有收益，不列为退路。

## 5. 契约与向量（H0 交付物）

与 v1 同样的工程方式：**一份规范 + 一份向量 + 三语言 parity**。

- 规范：`aimail-gateway/protocol/DID-REQUEST-PROTOCOL.md`
- 向量：`aimail-gateway/protocol/vectors/did-request.json`（确定性生成脚本，固定种子）
  分组：`signing_input`、`header`、`enroll_challenge`、`verdict`
- 覆盖的边界：空 body、4 KiB body、查询串含 `+`/空格/非 ASCII 全转义、
  多段路径、`t` 越窗、`addr` 与签名不符、`did` 非 `did:key`

## 6. 迁移计划（H 系列）

| 期 | 内容 | 回滚 | 验收 |
|---|---|---|---|
| **H0** 契约 | 规范 + 向量 + 三端空实现 | 删文件 | 三端读通向量 |
| **H1** did-sdk v0.4.0 | `sign_gateway_request` / `verify_gateway_request` + `GatewayAccess-v1` 注册助手；随 P1 的发布管线出包 | tag 回退 | 7 平台可装；向量全绿 |
| **H2** gateway 双栈 | 新提取器（Ed25519）+ 保留 v1 HMAC；`did_bindings` 表；`/api/v1/did/enroll`；指标 | 配置切回 `hmac` | 两种认证并行通过；错签/越窗/改地址全部 401 |
| **H3** SDK 切换 | pysdk/tssdk 优先用 DID 签名，配置可退回 v1 | `aimail_auth=hmac` | 存量 agent 不受影响 |
| **H4** 收口 | 观察期后（建议 ≥ 2 个发布周期）关闭 v1；删除 `key_hash` 路径 | 重新开启 | 无 v1 流量 |

**顺序上的硬约束**：H2 的 `did_bindings` 必须由绑定审批写入，所以 **H 依赖 P7 已跑通**。
这也是为什么建议不要把它塞进现在这轮。

### 6.1 每期门禁（在现有门禁之上追加）

- gateway：`cargo test` 全绿 + 新增认证矩阵测试（缺头/错 did/错 addr/越窗/重放/双栈并存）
- 三端：parity 向量测试（v1 与 v2 各一份，互不干扰）
- **渗透自检**：用一把"泄露的 `key_hash`"尝试签名 → 必须 401；用别人的 `did` 签 → 必须 401

## 7. 备选形态：挑战换短时会话令牌

不是二选一，而是性能退化时的优化项：

```text
登录：GatewayAccess-v1 挑战 → 200 {session_token, expires_in=900}
之后：Authorization: Bearer <session_token>（+ HMAC，密钥由挑战派生）
```

- 优点：稳态请求回到 ~1.8 µs；令牌不落库（内存/短期），泄露窗口 15 分钟。
- 缺点：**又引入了一个 bearer 凭据**（虽然短时），且增加会话状态与过期的失败模式。
- 判定：**当前不需要**。只有在"每请求签名"被实测证明是瓶颈时才启用，且它不改变信任模型：
  令牌是 DID 签出来的短期派生物，库里仍无共享秘密。
- 若启用，`did_bindings` 不需要改；会话表放内存、15 分钟过期，进程重启即失效（可接受）。

## 8. 难易度评估（按仓）

| 仓 | 工作 | 相对规模 | 风险点 |
|---|---|---|---|
| `did-sdk` | 请求签名/验签助手 + 注册助手（复用 `GatewayAccess-v1`） | 小 | 与 v0.3.0 同一条发布管线，需一起排期 |
| `aimail-gateway` | 新认证提取器、`did_bindings` 表、注册端点、双栈开关、指标 | **中偏大** | **全局鉴权路径**；`auth.rs` 1 182 行；错一次全站 401 |
| `pysdk` | 换签名器（`_signed_headers`）+ 配置开关 | 小 | 需保持 `dependencies = []`（Ed25519 靠 did-sdk extra） |
| `tssdk` | 同上（`api-signature.ts` + `gateway.ts`） | 小 | 同上 |
| 运维/文档 | 双栈说明、重新绑定流程、`did:key` 不可轮换的用户告知 | 中 | 容易被忽略，但这是用户能感知到的最大变化 |

**综合**：代码量约为 P4 的 0.6–0.8 倍，但**风险集中度更高**（鉴权路径）。不激进，但需要独立窗口与灰度。

---

## 9. 建议

### 9.1 现在做什么

1. **不并入 P0–P8。** 它与邮件签名正交，混在一起会让两个变更互相牵连回滚。
2. **现在只做一件低成本的事**：在 P7 的绑定审批流程里**顺手写 `did_bindings` 记录**
   （`did`、`address`、`system_id`、`scopes`、`active`、`approved_by`、`approved_at`）。
   这张表本来就要有（绑定是产品概念），H 开始时数据已经在了。

### 9.2 什么条件下提前

- 若出现"数据库被拖库"类安全要求，或合规要求"服务商不得持有可代表用户的凭据"——
  那就把 H 提到 P7 之后、P8 之前。
- 若只是在意外部干扰，DID 签名已经能挡住大部分风险，**不需要**为它提前。

### 9.3 不建议的做法

- **不要把 API key 从 DID seed 派生**（Q2 里的"路 1"）。它只省一次密钥传递，
  却把"轮换"彻底焊死，而且库里仍然是一个可冒充的共享秘密——**收益小、代价大**。
  要么保留 HMAC，要么换成签名；中间态不划算。
