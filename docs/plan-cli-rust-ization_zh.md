## 7 退役策略与对照物（owner 2026-10-06 提问）

**（A）断点处置：`address add|rm` 做壳 ✓**
- 形态：仅**注册子命令 + 参数面 + 反调契约位**；内部无实际动作。
- 规范（硬）：**不得静默成功** ✗ —— 被真实调用时必须产出**一行可见的"未实现/预留"结果**（rc=0 且打印 `reserved: not implemented`，或按调用意图返回 rc≠0），符合"能力不可用响亮失败"。

**（B）对照物评估（owner 2026-10-06 的裁剪）——唯一标准 = 5 个干净 agent 环境下"安装流程正常 + 维护子命令可用"**
- **结论：原版 python CLI 的参照价值有限、且有明确代价，应降级为"有时间盒的调试辅助"，不作为验收标准** ✓。
- 理由（成本/收益）：
  1. 验收标准本身**不需要**它：E2E journey 跑在**干净镜像**上（安装 + 各子命令），与"是否与旧 CLI 逐字节一致"无关 ✓；
  2. 旧 CLI **不是规范**（规范=本文件 + 网关/SDK 行为）；它自身也可能有缺陷 ✗，且 rust 移植处已按契约修正 ⇒ 逐字节对齐反而可能**锁死旧缺陷** ✗；
  3. 保留两实现的持续代价：门禁**双形态跑批时间翻倍** ✓、旧 CLI 自带 python 依赖（与目标相悖 ✗）、"谁是权威"的认知成本 ✓；
  4. **收益可用一次性手段替代** ✓：在删除前把行为固化为 **golden 快照**（一次抓取，长期复用 ✓），此后回归 = **干净环境 E2E + golden** ✓，不再需要旧代码 ✓。
- **时间盒（硬）**：`CLI_IMPL=python` 仅保留至 **①A 组闭合 ②golden 抓取完成** 为止；两者达成即**删除 python CLI（含门禁形态）** ⇒ 仓库单实现 ✓。
- 保留期间的唯一用途：**失败分类的辅助**（快速区分"rust 移植回归" vs "夹具/环境问题" ✓），**不作为 PASS 判据** ✗。

**（C）利弊**
- **利** ✓：零环境依赖（无 python）· 单产物（安装/升级简单）· CLI 与 SDK 无版本漂移 · 单一语言维护 · 体积小、启动快、确定性高 · 攻击面小。
- **弊（含缓解）** ✗：
  1. **失去行为 oracle** ⇒ 缓解：golden 固化 + 门禁保留 oracle 形态；
  2. **SDK 侧问题定位变难**（少了"用 python 直接戳 SDK"的便利）⇒ 缓解：门禁两形态 + SDK L2；
  3. **原 python CLI 承载的附带能力需重新归位**（如 MCP 载荷 `bin/mcp`、`runtime_core` 的载荷 stamping）⇒ 按目标：`bin/mcp` **移除**，MCP 支持改由 **SDK 侧**提供 ✓；载荷逻辑 rust 侧已有对等实现 ✓；
  4. **过渡期双实现成本**（门禁需同时维护两形态）⇒ 缓解：设明确退役时点（A 组闭合 + 五平台 L2 全绿 + golden 齐备后）。
- **结论**：**产品单形态（二进制）+ 门禁双形态（含 oracle）** 是代价最小且不丢基准的组合 ✓；"彻底抛弃原版"仅指**安装载荷**，不指**门禁基准** ✓。

## 8 兼容性与版本策略（SDK 重构发版对旧版可执行性的影响）

**结论**：SDK 收敛（6 op + 5 薄入口 → 3 op）**默认会破坏兼容** ✗，因此必须按下表执行，且**四条组合都要在门禁里跑** ✓。

| 组合 | 结果 | 硬要求 |
|---|---|---|
| 旧 CLI + 旧 SDK | ✅ 不受影响 | — |
| **旧 CLI + 新 SDK** | **必须可用** ✓ | 新 SDK **additive**：保留 6 个旧 op 与 5 个薄入口（改为**内部转调**新实现的薄包装），仅**新增** 3 个 op |
| 新 CLI + 新 SDK | ✅ 可用 | — |
| **新 CLI + 旧 SDK** | **必然失败** ✗ | CLI 必须**版本握手**（门内 `version`）⇒ 检测到 SDK 过旧时**响亮失败**并给出升级指引，**不得崩溃/静默降级** ✗ |

**发布纪律（四步边界序内执行）**
1. **加法优先**：新 SDK 版本 = 3 新 op **+ 全部旧入口保留**（弃用标注，≥1 个发布周期后再移除；移除属破坏性 ⇒ 走主版本）；
2. **薄包装而非复制**：旧入口一律转调新实现（单一实现，避免双份逻辑漂移）；
3. **CLI 侧版本下限检查**：`version` op 握手 + 明确错误文案（缺 op/版本过旧 ⇒ 指向升级 SDK）；
4. **门禁覆盖四组合**：尤其**旧 CLI + 新 SDK**（兼容性主战场）与**新 CLI + 旧 SDK**（失败必须可见且友好）；
5. **宿主环境前提**：新 SDK 的 python/node 版本要求不得高于旧版（`python_requires` / `engines` 显式声明），否则旧宿主装不上 ⇒ 属"可执行性"破坏 ✗。

## 9 双写期的复杂度与门禁升级（owner 2026-10-06 提问）

**（A）"两者兼得"（保留旧入口 + 新增 3 op）会增加多少复杂度？—— 小 ✓**
- **实证**：SDK 的门本就是**一张分发表**（`pysdk/sdk_ops.py:168-173`，op → 处理器 ✓）⇒ 本次改动 = **新增 3 行 + 6 行转调** ✓（旧 op → 新实现），**无逻辑复制** ✓。
- 真正成本在流程而非代码：① 弃用标注与移除时点管理 ✓；② 门禁需跑**四组合**（跑批时间上升 ✓）；③ 过渡期"看起来没收敛彻底"的认知成本 ✓。
- 控制手段（硬要求）：旧入口**只转调、不复制** ✓；op 名与处理器用**单一注册表**（避免手工分发 ✓）；弃用窗口**仅一个发布周期**并写死移除时点 ✓；四组合用**参数化矩阵**跑同一脚本（不写四套 ✓）。

**（B）新 SDK 版本会不会升级 SDK 的 L2 门禁？—— 会，且必须 ✓；但升的是"覆盖范围"，不是"门槛高度"**
| 门禁层 | 含义 | 本次变化 |
|---|---|---|
| SDK L1/L2（功能与集成） | 测试 SDK 自身行为 | **新增**：3 个新 op 的行为用例 ✓；**新增**：**旧入口兼容 smoke**（6 op + 5 薄入口仍可用 ✓ = 兼容性主证据） |
| SDK L3（发布物复核） | registry 上的 wheel/npm 复核 | 随版本重跑 ✓（版本号、文件集、依赖元数据 ✓） |
| 跨组合矩阵（旧/新 CLI × 旧/新 SDK） | 兼容性主战场 | **归 CLI 门禁** ✓（SDK 侧只负责"旧入口可用"这一半 ✓） |
| 门槛高度（PASS 判据） | — | **不变** ✗（不放宽、不提高 ✓） |

## 10 边界调整对 SDK 门禁的影响与锁定实现（owner 2026-10-06 关注点）

**(A) 门禁变更规模：结构不变，仅用例映射 + 新增 1 项棘轮**
| 门禁部分 | 变化 |
|---|---|
| SDK L1/L2 功能用例 | **基线=既有门禁（已保证内部流程正确 ✓）**；既有用例基本不动，仅在入口被合并处改指向；**目的=证明改动未破坏既有逻辑** ✓；宿主回归用例不变 |
| SDK L3 发布物复核 | 随版本重跑（版本号/文件集/元数据），脚本不变 |
| **新增**：边界棘轮 | 断言 §5(3) 四条；**一处实现、双向生效**（SDK 侧 + CLI 侧门禁各跑自己那半） |
| 门禁脚本/夹具 | 不变（分发表 `sdk_ops.py:168-173` 收敛后仍是同一张表） |
⇒ 结论：**SDK 门禁变更量小**（用例合并 + 1 项棘轮），不改门禁结构、不改 PASS 判据强度。

**（B0）顺序原则（owner 2026-10-06）**：SDK 门禁**第一序 = 既有内部流程/逻辑正确性（基线已具备）**，本次要求=**不破坏既有逻辑** ✓（主体）；**第二序 = 边界固化稳定**（附加棘轮）。二者**独立报告、不得混淆** ✗：功能门禁红 ⇒ SDK 实现问题；边界棘轮红 ⇒ 越界/接口漂移。**禁止**以边界断言替代或削弱功能验证 ✗（否则"顾此失彼"）。

**(B) 能否锁死 SDK 边界 —— 能，且是 CLI 正确性判断的前提**
- 锁定手段 = **边界棘轮（集合相等 + 白名单）**：
  1. 门的 op 集合 == {assemble, update, teardown}（多/少即红）；
  2. SDK 对系统级配置**只读**（禁写 path 级断言）；
  3. SDK→CLI 调用**白名单**（非白名单即红）；
  4. CLI 对绑定文件**只读**（禁写断言）。
- 收益（回答"对后续 CLI 正确性判断的影响"）：边界一旦锁死，**归属判定变成机械判定** ✓ —— 出现缺陷时，凡越界调用立即被门禁指认；未越界则问题必在该侧实现内 ⇒ 不再需要靠"对照旧 CLI"来推断 ✗（这也顺带取消了旧 CLI 的留存理由）。
