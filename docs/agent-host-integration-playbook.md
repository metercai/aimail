# 新 agent 系统对接经验汇总（可复用判定清单）

用途：拿到一个新的 agent 宿主（TUI / 桌面 / 网关 / IDE 插件…），在**写一行适配代码之前**，用本文的 10 个问题快速判定它是**多地址（M）**还是**单地址（S）**、该用哪种接入面、以及必须满足哪些约束。
来源：hermes、deerflow、dsh、pi、PI-Desktop 五个宿主的实战（含踩过的坑）。

用法建议：**先答 Q1–Q4（判定 M/S）→ 再答 Q5–Q10（决定接入面与契约）→ 最后用 §6 的约束清单当 DoD。**

---

## 1. 十个必答问题（附"怎么查"与"不合格的后果"）

| # | 问题 | 怎么查（可执行） | 不合格 ⇒ |
|---|---|---|---|
| **Q1** | 有没有**稳定的中间层容器**（workspace / project / profile / cwd 目录），地址能否绑在它上面？ | 找宿主概念表：`workspaceRegistry` / `project` / `projectId` / `sessions/<encoded-cwd>/`；看会话创建接口是否以"容器"为参数 | 无容器 ⇒ 只能 S（地址无落点，pause/move 语义无法表达） |
| **Q2** | 能否由**入站路径**创建新会话？ | 找宿主 API / CLI：`session.create`、`agents.create`、`--session-id`（creating otherwise）；确认调用者是"扩展/外部进程"而不是"仅 UI" | 不能 ⇒ 新 thread 无法独立成会话 ⇒ S 或按"新 thread 进当前会话"降级 |
| **Q3** | 能否由**入站路径唤起指定的既有会话**？**是否稳定**（目标会话正被别人用时？） | 找 `resume`/`attach`/`switch_session`/`turn/start{sessionId}`；**关键**：查会话文件/状态是否有锁/租约（`flock`、`native-pi-session-lease`、`sessions.get` 是否要求驻留） | 不稳定（无锁、探测不到第三方写者）⇒ **S**（硬约束不成立，不能靠适配层"凑"） |
| **Q4** | 谁**长期存活**、能承载 SSE？ | 看进程模型：每会话一进程（TUI）还是有常驻 host（桌面/服务）；扩展能否脱离会话运行；是否有 `background.service` 类权限 | 没有长期存活者 ⇒ 入站只在"用户开着"时有 ⇒ 必须明确写入限制，否则不算完成 |
| **Q5** | 注入语义：**排队**还是**打断**？是否幂等？ | 找 `admission`/`deliverAs`/`followUp`/`steer`/`idempotencyKey`；看是否"流式中必须显式传" | 只能打断 ⇒ 会在 agent 工作中途插话；无幂等 ⇒ 重投会重复执行 |
| **Q6** | 工具面怎么注册？**名字会不会被改写**？调用约定（位置参数/返回值类型）？ | 实测：注册 15 个工具后看模型可见的名字（可能被哈希成 `ext_…_<hash>`）；试位置参数与返回字符串 | 名字被哈希 ⇒ 提示词只能靠**工具描述**触发；返回类型错 ⇒ 模型读不到结果 |
| **Q7** | 安装与授权模型：安装命令是谁的？能力如何授予？agent 能否自助安装？ | 查安装入口（`pi install` / 插件中心 / `pip install`）、清单里的权限声明、安装期授权 UI | agent 可自助装 ⇒ **自我提权风险**，产品上应禁止，只留"引导" |
| **Q8** | 实例身份：AgentSystemId / 空间 id 从哪来？多实例如何隔离？ | 找 home/profile 目录、`agent_system_id`、`getSessionDir`、project 注册表 | 身份不稳定 ⇒ 每次重启都换绑定、聚合流失效 |
| **Q9** | 生命周期：pause / resume / unbind / 重启后能否自动 arm？ | 找快照/指针/绑定文件；实测重启后是否自动恢复（契约 C10/C12） | 解绑不停路由 ⇒ 幽灵投递 |
| **Q10** | 失败语义：宿主拒绝、宿主忙，如何表达？ | 找错误码/异常；确认"投递未成功"是否能被上层识别为**不 ack** | 拒绝被吞 ⇒ 邮件被认为已处理（静默丢信） |

## 2. M/S 判定矩阵（把 Q1–Q3 的结果直接映射）

| Q1 容器 | Q2 创建 | Q3 唤起（稳定） | 判定 | 说明 |
|---|---|---|---|---|
| ✅ | ✅ | ✅ | **M** | 地址绑容器；thread→session 路由；新 thread 新 session |
| ✅ | ✅ | ❌ | **S** | 只能"当前会话 + 单地址"（pi/TUI 就是这一格） |
| ✅ | ❌ | ✅ | **S（或受限 M）** | 新 thread 无处安放 ⇒ 需产品层确认是否允许"进当前会话" |
| ❌ | — | — | **S** | 无容器，地址没有落点 |

**稳定性的判据（Q3 的细则）**：唤醒路径必须满足"**可确定成功**或**可确定推迟**，且绝不双写"。
反例：pi/TUI 的 `SessionManager.open()` + `appendMessage()`——会话文件无锁、无法探测第三方写者 ⇒ 不安全 ⇒ 判 S。
正例：PI-Desktop 的 `turn/start{sessionId}`——只要求会话在持久层存在，宿主自行加载并取租约，忙时 `admission:"queue"` ⇒ 判 M。

## 3. 三种接入面，怎么选

| 接入面 | 适用 | 优点 | 代价 |
|---|---|---|---|
| **宿主扩展**（pi extension / hermes plugin） | 引擎本身支持扩展 | 引擎通用、换宿主还能用；工具面天然在模型上下文里 | 通常拿不到会话生命周期（pi: `NATIVE_PI_UNSUPPORTED`）⇒ 只能配 S |
| **宿主插件 / 后台服务**（PI-Desktop 插件） | 宿主有插件或后台服务机制 | 可常驻（承载 SSE）、可申请跨会话权限（`session.update.all`）、权限安装期一次授予 | 与宿主耦合、分发走宿主生态（非 npm pip）、上架审核不确定 |
| **外部守护 + 宿主协议**（RACP / `--mode rpc` / CLI） | 宿主暴露协议 | 不改宿主、可调试 | 需鉴权与配对；权限收敛（如 `remoteMaxPermissionMode`）可能把自动化压成逐步人工批准 |

**选型顺序**：宿主插件/后台服务（若可拿跨会话读写）＞ 宿主扩展 + 宿主协议补会话控制 ＞ 纯外部守护。
原则：**SSE 与"唯一写者"尽量同进程**；跨进程只在"宿主自己保证独占"时采用。

## 4. 投递契约（与宿主无关的公共部分）

```text
1. gateway_url + recipient → binding；无 / paused ⇒ 不 ack
2. 空间 = binding 绑定的容器（project / workspace / cwd 目录）
3. parent = In-Reply-To（立即父消息）
   last   = References 最后一个元素（无 In-Reply-To 时的父消息代理）
   root0  = References[0]（thread 根；**不能**用来判"直接回复"）
4. 直接回复 := parent ∈ outbound 索引（同 address + gateway）⇒ **必须**回该 session，禁止降级
5. 否则：thread 有历史 ⇒ 回"曾处理该 thread 的 session"（thread 可跨 session）
        无历史 ⇒ 新建 session；失败 ⇒ 回退当前会话（仅日志）；再失败 ⇒ 不 ack，留 pending
6. 宿主接受 ⇒ 写 thread 记录 + ack
```

**为什么把"直接回复"钉在 `In-Reply-To`**：只有"对方在回我这一封"才保证与原会话强相关；`References[0]` 恒为线程根，用它判会把"我们发起线程后的隔代回复"误判成直接回复。

**幂等**：优先用宿主的 `idempotencyKey`（带输入哈希）；没有就本地记 `email:<message_id>`（LRU + 落盘）。

## 5. 踩坑清单（症状 → 根因 → 查法）

| 症状 | 根因 | 查法 |
|---|---|---|
| 入站 turn 全 401 / 模型毫无响应 | 宿主只读**配置文件里的密钥**，不读环境变量（deerflow `models[].api_key`） | 看宿主日志的鉴权错误；把占位符留在配置里跑一次 |
| 邮件被拉走但**永不 ack**，队列不排空 | 适配层把 run 提交到"自己以为的端口"（默认端口 vs 实际 `--port`） | 看宿主日志里投递之后是否**没有任何后续**；核对自调用地址 |
| 证据自相矛盾：`max=0 final=0`（像没排队） | ack 发生在**启动瞬间**，探针启动太晚 | 让探针跨过启动窗口（启动前起 watcher） |
| 两个进程写同一会话，上下文分叉 | 宿主会话文件**无锁** | 检索 `flock`、`.lock`、`O_EXCL` 等关键字；看是否有租约/独占打开 |
| 扩展里"创建会话"直接抛错 | 宿主只在**用户发起命令**的上下文里开放会话控制（pi: `NATIVE_PI_UNSUPPORTED`） | 读类型定义里命令上下文与事件上下文的差异 |
| 新模块"本地能 import，容器里 cannot import" | 打包是**手写清单**，漏了新文件 | 解包 wheel/tgz 逐文件比对源码树 |
| 断言长期红，被当成"无关" | 测试把**宿主文案/端口/哈希名**钉死 | 断言改为**不变量**（能力、语义），不钉具体字符串 |
| 判定"宿主不支持 X"，其实是夹具问题 | 夹具用了**非用户的安装方式**（伪造目录插件） | 用真实安装路径复跑；对照宿主官方文档的机制列表 |
| 单地址宿主"从来没有被问过"第二地址 | 门禁对单地址宿主跳过了第二次申请 ⇒ s4 只是空过 | 所有宿主都申请第二个 code，并要求看到**书面拒绝**（否则 RED） |
| 能力声明加上了，守卫却不生效 | 打包后同一模块有两份实例，内存态分裂 | 能力声明走**环境变量**通道并让环境优先；单测 + L2 各验一次 |
| 拒绝发生了，证据里却没有 | 夹具只保留最后一轮日志，中间轮次被覆盖 | 每轮单独落盘（`turn_N.log`），断言按语义匹配而非精确 token（模型会转述） |

## 6. 对接约束条件（最终清单，作为 DoD）

### 6.1 能力（决定 M 还是 S）

- **C1** 必须存在**稳定容器**（workspace / project / profile / cwd 目录），地址绑定在该容器上；容器标识必须可持久化且跨重启稳定。
- **C2** 会话创建必须由**入站路径可调用**的接口提供（宿主 API / 插件 API / CLI）；仅 UI 可创建不算。
- **C3** 会话唤起必须对**未驻留会话**可用，且**宿主是唯一写者**（有锁/租约/独占打开）。
- **C4** C2 或 C3 任一不满足（或 C3 不稳定）⇒ **必须降级为 S**，并按 S 校验（拒绝第二地址，不消耗激活码）；**禁止**用外部进程/spool/心跳等适配层机关去"凑"稳定。
- **C5** 必须明确"谁长期存活并承载 SSE"；若只有会话进程存活，须在契约中写明"无活会话时无入站"。

### 6.2 契约

- **C6** 每 `(AgentSystemId, Gateway)` **一条**聚合流；逐投递按 recipient **重读绑定**（pause/archive 立即生效）。
- **C7** **只在宿主接受后 ack**；拒绝必须表现为错误或 `skip`（不 ack 不报错），**不得静默丢弃**。
- **C8** 直接回复（`In-Reply-To` 命中我方出站 Message-ID）**必须**回到原 session，禁止降级；隔代回复按 thread 走；新 thread 优先新 session；创建失败按"回退当前会话 → 不 ack 重试"逐级降级。
- **C9** thread 记录按 `(address, gateway)` 隔离；binding **不保存** session（session 可弃用）。
- **C10** 必须有幂等：宿主 `idempotencyKey`（带输入哈希）或本地 `email:<message_id>`，防重复投递。

### 6.3 安全

- **C11** 安装走**宿主自身机制**，能力在**安装期由用户授予**；agent **不得**自助安装或自我提权（`pi install` 类命令可作为产品能力禁止）。
- **C12** 凭据**运行时注入**，不烘焙进镜像/包，不落日志；高危能力（跨会话读写、shell、桌面控制）必须显式授权并分级提示。
- **C13** 权限参数必须**白名单校验**（如 `scope` 只接受 `own`/`all`，写错报错而非放宽）。

### 6.4 工程

- **C14** 打包清单与源码文件**一一对应**，并有守护测试（新增模块漏打包必须单测红）。
- **C15** 门禁用例的任何改动必须在交接文档标注"**是否放宽判定**"；放宽需审批，不得由开发默认执行。
- **C16** 断言只钉**不变量**（能力/语义/数量关系），不钉宿主的可变量（文案、默认端口、被哈希的工具名）。
- **C17** 每个阶段可复现：落盘日志 + 一条可粘贴的复现命令；证据目录不进仓库、交接文档只写"以你自己那轮为准"。
- **C18** 夹具不得**自造**产品缺陷：必须用用户真实的安装/调用路径（目录插件、伪造端口这类捷径会制造假判定）。

## 7. 一页纸 DoD（新宿主接入完成的条件）

```text
[ ] Q1–Q10 全部有书面答案，每条附代码位置或实测日志
[ ] M/S 判定写入契约 §11，且与 addressModel 自洽（声明与能力一致）
[ ] 每 (AgentSystemId, Gateway) 一条聚合流；SSE reconcile 行稳定
[ ] 直接回复落回原 session（同一会话文件，消息数 +1）
[ ] 新 thread 新 session；创建失败时的降级路径可复现
[ ] pause / resume / unbind 生效；重启后自动 arm
[ ] 拒绝/忙/未知 三种失败各有可区分的行为（不 ack / 排队 / skip）
[ ] 幂等：同 message-id 重投只生效一次
[ ] 安装与授权模型写入文档；agent 无法自助提权
[ ] 打包守护测试通过；门禁用例改动已标注
[ ] 全量回归：本宿主 + 至少一个既有宿主未变红
```

## 8. 附：判定时最容易被忽略的三件事

1. **"能创建" ≠ "能稳定唤起"**。前者查接口存在，后者要查并发语义——pi 两者都有接口，但无锁 ⇒ 仍判 S。
2. **"扩展能跑" ≠ "扩展能做会话路由"**。多数引擎的命令上下文才给会话控制，事件上下文不给；先读类型定义的两个 context。
3. **"宿主拒绝"必须能被上层看见**。适配层最容易犯的错是把失败吞掉，导致"邮件消失"；这也是 ack 语义必须前置定义的原因。

## 9. 共用 SDK 如何识别"当前是哪种 agent"（四层，各司其职）

tssdk / pysdk 同时服务多个宿主，识别不能靠单一"猜"，而是四层分工。**混用是最常见的错误来源**。

| 层 | 回答什么 | 机制 | 代码位置 |
|---|---|---|---|
| **L0 入口装载** | 谁把我加载起来？ | **宿主自己的 loader 决定**（entry point / 插件目录 / 插件中心），SDK 不猜 | `hermes_agent.plugins`、`deerflow.extensions`、pi 扩展目录、PI-Desktop 插件中心 |
| **L1 断言** | 我声明自己是 X，环境真的是 X 吗？ | `activateHost(declared)` + `detectHost()`：强信号 = 宿主 SDK 可解析；弱信号 = `$HOME/<configDir>` 存在；**多宿主并存时 `verified=false`，只告警不误判** | tssdk `hosts/activate.ts:52-66`、`hosts/detect.ts` |
| **L2 实例身份（AgentSystemId）** | 我是哪个实例？ | 由**宿主 home**（profile / 数据目录）+ 机器指纹派生 `sha256`；可用 `AIMAIL_AGENT_SYSTEM_ID` / `AIMAIL_HARDWARE_FINGERPRINT` / `AIMAIL_AGENT_HOME` 覆盖；宿主插件通过 `set_agent_home_resolver` 注入 home | pysdk `v2/agent_system_id.py:29-90`；tssdk `core/agent-system-id.ts:73` |
| **L3 对外身份** | 网关侧看到谁？ | `X-AIMail-Agent: <platform>/<version>`；版本用 `--version` 探测，探测不到就是 `unknown/unknown`（**不猜、不伪造**） | pysdk `aimail_tools.py:1173-1212`（`_AGENT_DETECTORS`） |
| **L4 能力画像** | 这个宿主能做 M 还是只能 S？ | 宿主声明 `address_model`（single/multi）；新宿主需再声明**会话能力**（可创建 / 可稳定唤起） | `set_binding_context_provider`；契约 §11 |

### 9.1 关键纪律

1. **L0 不用探测结果选入口**。tssdk 注释写明：detection 的两个用途是"断言装错宿主"和"直接 import 时诊断"，**不是**用来选择哪个 entry 运行。
2. **L2 必须用宿主 home，不能用 cwd**。pi 的 cwd 是"会话容器/workspace"，同一实例可开多个 cwd ⇒ 用 cwd 派生 ASID 会让同一实例变成多个身份（聚合流失效、绑定互不可见）。
3. **L3 探测失败要显式降级**（`unknown/unknown`），不要回落到某个默认名字，否则归因数据被污染。
4. **L4 必须随能力变化**：同一引擎的不同承载形态（裸 pi vs PI-Desktop）能力不同，必须由**能力探测**而非"引擎名"决定（否则会把 S 误判成 M）。

### 9.2 接一个新宿主时，必须提供的五件事

```text
1. 入口        entry point 或插件入口（让宿主 loader 选中我们）
2. 空间        home / profile / project 的解析方式（决定 L2 与地址绑定落点）
3. 能力        可创建会话？可稳定唤起会话？⇒ 声明 address_model / session_*
4. 身份串      platform/version 的来源（--version、SDK 版本、宿主常量）
5. 断言信号    （可选）宿主 SDK 包名或 config 目录，供 L1 检测"装错宿主"
```

缺 1/2 ⇒ 无法稳定安装与隔离；缺 3 ⇒ 只能按最保守的 S 处理；缺 4 ⇒ 归因失真；缺 5 ⇒ 装错宿主时静默跑在错误环境里。

## 10. 识别层的三条硬经验（补 §9，务必内化）

1. **"引擎名"不能替代"能力探测"**。裸 pi 与 PI-Desktop 是同一个 pi 引擎，但前者是 S、后者是 M。凡是用宿主名字/引擎名去决定 M/S 的代码，迟早误判；必须探测能力（能否创建会话、能否稳定唤起、能否常驻）。
2. **`cwd` 是空间，不是实例身份**。pi 的会话按 cwd 分目录、地址也绑 cwd——这是"空间"；而 AgentSystemId 必须由**宿主 home**派生。若把 cwd 当身份：一个实例开两个 workspace 就变成两个身份 ⇒ 聚合流裂开、绑定互不可见。
3. **L4 能力位目前只有 `address_model`，不够**。这次判定证明必须再加**会话能力**（`session_create`: 可创建 / 可稳定唤起）。缺这一位，下一个宿主仍会被硬塞进"M 或 S"的二元判断里，而无法表达"能创建但不能稳定唤起"这种真实存在的能力组合（pi/TUI 就是）。

> 结论：契约 §11 的"多地址前置能力"必须是**可探测、可声明、可校验**的三件事汇总 —— 空间稳定性、地址可绑定、会话可创建/可稳定唤起。任何一项靠"看起来支持"来判断，都会在并发场景下崩掉。
